1. System Architecture Overview

MobileHub is engineered following an enterprise-grade, decoupled 3-Tier Client-Server Architecture:

+-------------------------------------------------------------------------------+
|                        TIER 1: PRESENTATION LAYER                             |
|         Vanilla HTML5, CSS3, & Modern ES6+ JavaScript (Zero Frameworks)       |
|            Deployed Globally on GitHub Pages CDN with Auto SSL                |
+-------------------------------------------------------------------------------+
                                        │  (HTTPS REST Calls)
                                        ▼
+-------------------------------------------------------------------------------+
|                        TIER 2: APPLICATION LAYER                              |
|                   Node.js Runtime + Express.js Framework                      |
|                  Deployed on Render Cloud Web Service (Linux)                 |
|     Features: Connection Pool, JWT Auth Middleware, CORS, ACID Transactions   |
+-------------------------------------------------------------------------------+
                                        │  (Encrypted TLS over Port 4000)
                                        ▼
+-------------------------------------------------------------------------------+
|                           TIER 3: DATA LAYER                                  |
|         Production: TiDB Cloud Serverless MySQL Cluster (AWS Tokyo)           |
|            Local Development: MySQL 9.x Server (localhost:3306)               |
|      Tables: users, products, orders, order_items with Referential FKs         |
+-------------------------------------------------------------------------------+

3. Technology Stack & Technical Rationale

Each technology in MobileHub was deliberately chosen based on software engineering principles and project requirements:

Why Node.js & Express.js instead of Python (Django/Flask) or Java (Spring Boot)?

  • Full-Stack JavaScript: Using JavaScript across client and server eliminates mental context switching, allows seamless JSON interchange, and simplifies testing.
  • Asynchronous Event-Driven Architecture: Node.js handles thousands of concurrent catalog and cart requests with zero thread-locking and minimal RAM consumption.
  • Lightweight Cold Starts: Express starts up in under 500ms on cloud containers, compared to Java Spring Boot which takes 15–30 seconds to initialize JVM classes.

Why MySQL (Relational) instead of MongoDB (NoSQL) or SQLite?

  • Strict ACID Transactions for E-Commerce: If a customer orders a smartphone, decrementing inventory and writing the order must be atomic. If stock is insufficient, the transaction rolls back cleanly. MongoDB lacks strict tabular constraints, risking data inconsistencies.
  • Foreign Key Integrity: Cascading foreign keys (user_id, order_id, product_id) guarantee that no orphaned order items can exist if records are deleted.
  • Why Migrated from SQLite: SQLite locks the entire database file during writes, making it fail under concurrent requests, and cannot run on ephemeral cloud hosting where disks reset. MySQL with connection pooling is enterprise-standard.

Why Vanilla HTML, CSS & JavaScript instead of React or Angular?

  • Zero Build Complexity: Native ES6 runs directly in browsers with zero bundlers (Webpack/Vite), avoiding fragile dependencies and breaking version changes.
  • Peak Performance: 100/100 Google Lighthouse speed rating with instant first contentful paint (FCP) under 300ms.
  • Demonstrates Core Fundamentals: Proves strong command of core DOM manipulation, asynchronous Fetch API, event delegation, and modern CSS Grid/Flexbox layouts.

6. Evaluation & Viva Presentation Guide

Examiner Question Recommended Model Answer
Q1: How does the order placement prevent race conditions and overselling? The order placement endpoint implements a MySQL transaction using getConnection() and beginTransaction(). It queries live stock with row-level locks, checks if inventory is sufficient, inserts the order and line items, decrements stock (stock = stock - ?), and then commits. If stock is insufficient, it executes rollback().
Q2: How are customer passwords stored securely? Passwords are never stored in plaintext. The backend uses the bcryptjs library with a salt work factor of 10. This generates a cryptographically secure, one-way adaptive hash that is resilient against rainbow-table attacks.
Q3: How does authentication and role protection work? Upon successful login, the server signs a JSON Web Token (JWT) containing the user's ID, email, and role (customer or admin). On protected routes, an Express middleware verifies the Authorization: Bearer <token> header before granting access.
Q4: How do you prevent SQL Injection attacks? All SQL operations use parameterized queries and prepared statements (? placeholders) via mysql2/promise. User input is treated strictly as data literals and never concatenated into raw SQL strings.
Q5: Why is the backend deployed on Render while the frontend is on GitHub Pages? Separating concerns: GitHub Pages provides free, globally distributed edge caching for static assets (HTML/CSS/JS). Render provides continuous container execution for the dynamic Node.js runtime with free TLS certificates. This ensures high availability and zero hosting costs.
